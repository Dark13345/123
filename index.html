Как работает наша сетка

В момент запуска робот берёт текущую цену за центр и расставляет вокруг неё лимитные ордера через равный шаг: ниже центра — на покупку, выше — на продажу. У каждого ордера тейк-профит ровно на один шаг ближе к центру. Стоп-лосса у ордеров нет. замер

  1. Цена опускается и задевает уровень покупки. BUY LIMIT превращается в открытую покупку. Её тейк-профит — уровень выше, на шаг ближе к центру.
  2. Цена возвращается на шаг вверх. Покупка закрывается по тейку с прибылью в один шаг. Робот тут же ставит на освободившийся уровень такой же BUY LIMIT.
  3. Выше центра всё зеркально: продажа открывается при росте цены и закрывается, когда цена откатывает на шаг вниз.
  4. Пока цена ходит туда-обратно внутри сетки, робот снова и снова зарабатывает по одному шагу на каждом уровне.

  • Пауза (с 21.10). В меню «Управление» робота: новых ордеров нет, отложенные снимаются, открытые позиции на выбор — оставить, закрыть прибыльные или закрыть все.   • Шаг подбирают под инструмент. Меньше спреда нельзя: сделки не окупят спред. Слишком широкий шаг — сделок не будет вовсе, как у робота №3 ниже.

Итого

Сетка зарабатывает по одному шагу каждый раз, когда цена задевает уровень и возвращается. Прибыль сделки = шаг × лот: у наших роботов $0,30 на EURUSD и около $3 на золоте.

Убыток сетка получает при сильном движении в одну сторону: позиции копятся против цены, а стоп-лосса у ордеров нет — ограничить убыток можно только общим стоп-лоссом робота. Шаг — главный параметр: он должен быть больше спреда и меньше обычного движения цены за час-два.

Как управлять многими серверами

Вопрос: при 100 клиентах серверов станет много — как ими управлять, следить, куда денется клиент, если на сервере кончилась память, и как их все перезапускать? Ответ: серверами управляет сам сервис, а не человек. Сейчас всё работает на одном нашем сервере в одном процессе. Стенд сам поднимается после сбоя и перезагрузки, но при выкладке нового кода перезапускается — почти каждый день, потому что мы каждый день меняем код. Роботов на счетах NPB это не останавливает: их терминалы — отдельные программы. В рабочем сервисе выкладка будет реже и по очереди.

Сколько будет серверов

На Cloud VPS 6, как наш сервер, помещается около 20 роботов на счетах NPB (замер в часы новостей, см. «Сколько роботов помещается на сервер»; по замеру 20.10 — около 25). 100 клиентов по одному роботу — это 5 рабочих серверов и один центральный, около €73 в месяц с Windows при договоре на 24 месяца. 1000 клиентов — около 50 серверов, по замеру 20.10 — около 40. оценка

Если на сервере кончается память

  1. Не доводить до этого. Диспетчер ставит новый счёт туда, где больше всего свободно, и не заполняет сервер выше ~70% — запас на часы новостей. оценка

  3. Сервер упал целиком. Агент не отвечает — диспетчер переносит все его счета на остальные серверы и шлёт уведомление.
  4. Место кончается везде. Сервис сам заказывает новый сервер через API Contabo из готового образа, где всё уже установлено, — или пока просто пишет в Telegram «нужен сервер». У Contabo есть API для заказа и управления серверами. источник

Почему не придётся перезапускать все серверы

  • Обновление одной командой. Скрипт выкладывает новую версию на серверы по очереди, чтобы роботы не встали разом. Или агенты сами забирают новую версию с центрального сервера.
  • Перезапуск сайта не трогает терминалы. Поменялся код сайта — перезапускается только центр, роботы на рабочих серверах торгуют дальше.
  • Данные обновляются сами: статистика, балансы и отчёты считаются фоновыми задачами, перезапуск для этого не нужен.
  • Самовосстановление. Сервис стенда и агент — службы Windows: сами поднимаются после сбоя и перезагрузки. Зависший терминал агент перезапускает сам — замирания мы уже ловим на стенде. Плановая перезагрузка серверов — ночью в выходные, по очереди.

Как следить

  • Панель серверов в админке: список серверов, загрузка, сколько счетов на каждом, что упало. Делаем сами, данные от агентов.
  • Уведомления в Telegram: сервер не отвечает, память выше 85%, нет цен дольше 5 минут, терминал завис и не поднялся.
  • Готовые системы, если понадобится больше: Uptime Kuma (простая проверка «жив или нет»), Zabbix, Grafana с Prometheus — ставятся на центральный сервер.

Путь без терминалов: Manager API брокера NPB

Manager API — это программный доступ к серверу MetaTrader со стороны брокера. Через него работают CRM брокеров, системы контроля рисков и сервисы копирования сделок. Доступ выдаёт сам брокер: создаёт логин менеджера с нужными правами и разрешает подключение с наших IP-адресов. источник

Сейчас: терминал на каждый счёт

Для каждого счёта клиента на нашем сервере работает отдельная копия MT4 с советником. Терминал входит в счёт по паролю клиента, робот торгует изнутри терминала. Так же устроены другие сервисы роботов. замер

С Manager API: одно подключение

Наш сервис один раз подключается к серверу NPB как менеджер и видит все счета, которые клиенты к нему привязали. Робот — программа на нашем сервере — сам ставит и снимает ордера на этих счетах. Терминалы не нужны. оценка

  2. Клиент в нашем кабинете привязывает счёт NPB и подтверждает согласие на торговлю роботом. Торговый пароль от счёта ему вводить не нужно.

Варианты для Демо-счетов Tavio

  1. Оставить как есть. По оценке, 1000 пользователей выдержит один процесс. Проверить нагрузочным тестом: запустить 1000 фиктивных роботов на копии стенда и замерить память и процессор. оценка
  2. Считать роботов пачкой по инструменту. Пришла цена EURUSD — обработать сразу всех роботов на EURUSD; цена не изменилась — ничего не считать. Нагрузка зависит от числа сработавших ордеров, а не от числа роботов. оценка
  3. «Засыпание» роботов у неактивных пользователей. Не заходил 7 дней — робот не держится в памяти, при входе результат пересчитывается по истории минутных свечей. Минус: по свечам результат немного приблизительнее, чем по тикам. оценка
  4. Считать результат, только когда смотрят. Робот вообще не работает в фоне: при открытии страницы его результат прогоняется по истории цен с момента запуска. Без зрителей нагрузки нет. Минус: для точности нужна история тиков, а по свечам — приблизительно. оценка
  5. Хранить состояние роботов в базе, а не в отдельных файлах. Писать реже и пачкой — меньше нагрузки на диск, когда роботов тысячи. оценка
  6. Вынести демо-биржу на отдельный дешёвый Linux-сервер. Сайт и терминалы MT4 не мешают демо-бирже, и наоборот. оценка
  7. Лимиты по тарифу. Например, бесплатно один демо-робот, автоостановка через 30 дней без входа, больше роботов — на тарифе.

Варианты для счетов NPB — здесь нагрузка действительно большая

  1. Не давать всем демо-счёт NPB с терминалом. Новичок торгует на Демо-счёте Tavio, терминал MT4 включается только для реального счёта NPB.
  2. Договориться с NPB об API на их стороне — Manager API или серверный плагин. Тогда сделки по счетам клиентов идут через одно подключение, без терминала на каждого. Это главный вариант для 1000 клиентов, но он зависит от брокера: подробно — в разделе «Путь без терминалов: Manager API».
  3. Включать терминал, только пока робот работает. Нет запущенного робота — терминал выключен. Для ручной торговли так уже сделано: терминал счёта без робота работает, пока открыта «Торговля», и ещё 30 минут.
  4. Облегчить терминал: меньше истории и графиков, без новостей. Примерно 40–50 МБ вместо 71 — в полтора раза меньше, проблему не решает. оценка
  5. Терминалы на Linux через Wine в контейнерах. Сервер дешевле, чем Windows, но памяти на терминал столько же. оценка

Демо-счёт Tavio уже сейчас не требует сервера на каждого пользователя: это запись в базе, а все демо-роботы считаются в одном процессе. На 1000 пользователей хватит вариантов 1–3 из первого списка, вариант 4 нужен, только если пользователей станет на порядок больше. вывод, не проверено

  1. Журнал событий — таблица в базе стенда: регистрация, запуск робота, тариф, стёртый билет, остановка робота. Часть этих данных уже есть.
  2. Правила триггеров: событие, условие, задержка, шаблон. Например: «зарегистрировался, робота нет 24 часа — письмо „Запустите первого робота“».
  3. Очередь отправки — фоновый поток в процессе стенда, как демо-биржа: защита от дублей, лимит (не больше одного маркетингового письма в день на человека), тихие часы по часовому поясу.
  4. Шаблоны на Jinja2 + MJML: вёрстка не ломается в Outlook и Gmail, бренд Tavio, светлая и тёмная версии.
  5. Отписка: ссылка в каждом письме и заголовок List-Unsubscribe для отписки в один клик — его требуют Gmail и Yahoo для массовых рассылок источник. В профиле — настройки «какие письма получать».
  6. Список запрета: возвраты, жалобы и отписки приходят от почтового сервиса вебхуком, по таким адресам больше не пишем.
  7. Статистика: открытия (пиксель; Apple Mail искажает эти данные источник) и клики через нашу ссылку-переадресацию — видно, какое письмо приводит к шагу.
  8. Домен отправителя: отдельный поддомен, например mail.домен-сервиса, с SPF, DKIM и DMARC — репутация рассылок не испортит основной домен. Потом можно добавить BIMI — логотип отправителя в Gmail.

Вход через Google, Apple и Facebook: как подключить

Сейчас кнопки «Продолжить с Google / Apple / Facebook» работают в демо-режиме: окно похоже на настоящее, но к провайдеру стенд не обращается, учётка создаётся только у нас. замер Код настоящего входа уже написан: как только на сервере появятся ключи провайдера, его кнопка начнёт вести на настоящий вход. Перезапуск для этого не нужен. замер

Что нужно для любого провайдера

  1. Свой домен компании вместо временного 13-140-155-71.sslip.io, например app.tavio.…. Провайдеры проверяют домен, а временный адрес Apple и Facebook, скорее всего, не примут. вывод, не проверено
  2. Страница политики конфиденциальности и способ попросить удалить свои данные. Страница есть: /legal/privacy (адрес /privacy ведёт туда же), рядом — условия, согласие, риски и оплата. Реквизиты оператора, применимое право, условия возврата и почта поддержки пока помечены «уточняется»; текст нужно согласовать с юристом. замер
  3. Почта поддержки, которую увидит человек на экране входа провайдера.
  4. Ключи от провайдера — пара «номер приложения + секрет». Их кладут только в файл C:\RoboStand\oauth.json на сервере: в чат, почту и архивы для коллег не отправлять. Кто знает секрет, может выдавать себя за наш сервис.
  5. Адрес возврата для каждого провайдера: https://<домен>/api/oauth/<google|apple|facebook>/callback. Он должен совпасть до символа, иначе провайдер вернёт ошибку.
